## II. Architecture Deep Dive

### 2.1 HTAP Pattern (Hybrid Transactional/Analytical Processing)

```
User Application
    ↓
[Events/Traces Ingestion]
    ↓
PostgreSQL (Operational)      Tinybird (Analytical)
├─ Sessions                   ├─ Canonical Events
├─ Authentication             ├─ Time-Series Data
├─ User Preferences           ├─ Aggregations
├─ Real-Time Queries          └─ Historical Analysis
└─ Immediate Availability
```

**Decision Rationale:**

- **PostgreSQL (Neon):** Immediate read-after-write consistency, user sessions, authentication
- **Tinybird (ClickHouse):** Optimized for time-series analytics, 100M+ event scale
- **Async Forwarding:** Decouple operational response times from analytical workloads

**Implementation Details:**

- Store all trace data immediately in PostgreSQL (don't wait for ML analysis)
- Async background job forwards to Tinybird for analytics
- Dashboard queries fall back to PostgreSQL if Tinybird unavailable
- Conversation/session tracking in both databases for redundancy

### 2.3 Multi-Format Span Representation

The system represents spans in multiple formats simultaneously for frontend flexibility:

**1. Hierarchical Tree** (Parent-child relationships)

```json
{
  "id": "trace-123",
  "type": "trace",
  "children": [
    {
      "id": "llm-call-1",
      "type": "llm_call",
      "children": [
        {
          "id": "retrieval-1",
          "type": "retrieval"
        }
      ]
    }
  ]
}
```

**2. Flat Array** (Frontend compatibility)

```json
{
  "spans": [
    { "id": "trace-123", "position": 0 },
    { "id": "llm-call-1", "position": 1, "parentId": "trace-123" },
    { "id": "retrieval-1", "position": 2, "parentId": "llm-call-1" }
  ]
}
```

**3. Lookup Indices** (Fast access)

```json
{
  "spansById": { "llm-call-1": {...} },
  "spansByPosition": { "1": {...} },
  "spansBySpanId": { "original-span-id": {...} }
}
```

**4. Agent-Prism Format** (Visualization)

```json
{
  "type": "llm_call",
  "title": "OpenAI GPT-4",
  "badge": {
    "label": "LLM",
    "color": "blue"
  },
  "details": {
    "model": "gpt-4",
    "tokens": 1250,
    "cost": 0.045
  }
}
```

**Design Benefit:** Frontends use the format most convenient for their use case; no need to redesign backend.

- JWT token validation on all API endpoints

- CORS configuration for serverless environment

### Multi-Tenant Isolation

```typescript
// Every query includes tenant_id filter
SELECT * FROM traces
WHERE tenant_id = {uuid_of_authenticated_user}

// Caching includes tenant_id
const cacheKey = `dashboard:${tenant_id}:${hash(filters)}`

// Secrets scrubbing per tenant
scrubSecrets(trace.data, tenant.sensitivity_rules)
```

**Security Layers:**

1. JWT token validation (is user authenticated?)
2. Tenant ID extraction from JWT
3. Tenant ID validation (is UUID format valid?)
4. Query filtering (append WHERE clause)
5. Cache validation (check tenant_id in cache key)
6. GDPR deletion strategy (trace_index table for compliance)

### SQL Injection Prevention

- UUID format validation before using in queries
- Prepared statements for all dynamic queries
- Input length limits (PayloadSizeLimit: 5MB)
- Request signing for API keys

### After Optimization (Jan 4)

- **Dashboard queries:** ~300-500ms (cache hit) - **6x faster**
- **Schema initialization:** Removed from request path
- **Request overhead:** Reduced from 5500ms to &lt;100ms

### Caching Strategy

```typescript
// Session Cache (5 minute TTL)
const sessionKey = `session:${token}:${tenant_id}`;
const session = await cache.get(sessionKey);
if (!session) {
  session = await db.query("SELECT * FROM sessions WHERE ...");
  await cache.set(sessionKey, session, 300);
}

// Dashboard Cache (1 minute TTL)
const dashboardKey = `dashboard:${tenant_id}:${hash(filters)}`;
const data = await cache.get(dashboardKey);
if (!data) {
  data = await getDashboardMetrics(filters);
  await cache.set(dashboardKey, data, 60);
}

// Cache invalidation
await cache.delete(`session:${token}:*`); // On logout
await cache.delete(`dashboard:${tenant_id}:*`); // On password change
```

## IX. Key Bug Fixes & Learnings

### Critical Fixes

1. **Trace Data Preservation (Jan 1)** - Use COALESCE in UPDATE queries to preserve existing data
2. **Child Span Click Handlers (Jan 7)** - Enhanced spansById indexing with multiple lookup patterns
3. **Orphaned Spans (Jan 7)** - Filter root traces with isRootTrace flag
4. **Feedback JSON Parsing (Jan 6)** - Handle both string and object attributes_json
5. **Tinybird Rate Limiting (Jan 4)** - Return empty array instead of throwing on 429

### Lessons Learned

- ✅ HTAP pattern essential for separating operational and analytical workloads
- ✅ Caching strategy critical for serverless performance (no persistent connections)
- ✅ Multi-format span representation enables frontend flexibility
- ✅ Feedback metrics as primary issue signal (users click thumbs more than reading logs)
- ✅ Error context stack must include everything: what, how, when, why, how to fix
- ✅ Tenant isolation requires constant vigilance (check every query)
- ✅ Tinybird's TSV format requires custom parsing (not JSON)
- ✅ PostgreSQL NULL values need COALESCE in UPDATE statements
